# Отчет 
## 1. Задача

Диспетчер сервисной службы получает модель оборудования и код ошибки. Чтобы отправить инженера с нужной деталью, ему нужно определить неисправный узел, найти номер детали, проверить ее замену, а затем узнать цену и остаток на складе. Ассистент выполняет этот поиск и готовит заказ, который подтверждает человек.

Сведения распределены между несколькими источниками. Руководство описывает деталь, установленную изначально, сервисный бюллетень - ее замену, а ERP - актуальные цены и остатки. Например, при ошибке E-17 на AR-210 требуется пусковое реле. В руководстве оно обозначено как P-1042, но бюллетень предписывает использовать P-1042B. Ответ должен учитывать оба документа.

## 2. Выполненная часть

При построении индекса из документов извлекаются сущности и связи, а для групп связанных сущностей создаются сводки. Поиск использует связи или сводки, а агент дополняет его запросами в ERP.

| Модуль | Предназначение |
| --- | --- |
| src/assistant/graphrag/extraction.py | Доработка извлечения, нормализация, фильтрация, повторы, подсчет отброшенных элементов, разбор явных структур руководств |
| src/assistant/graphrag/communities.py | Разбиение графа и сводки с рассчитанной программой статистикой |
| src/assistant/graphrag/search.py | Локальный и глобальный поиск, замены и поставщики, источники, контекст линейки и проверка ответа |
| src/assistant/agent/tools.py | Пять инструментов поиска и ERP с проверкой аргументов |
| src/assistant/agent/agent.py | Цикл агента, лимит шагов, кеш вызовов, повторы ERP, подтверждение заказа и проверка ответа |
| Проверка | Тесты, оценка четырех режимов, разбор ошибок и подготовка артефактов |

## 3. Решение

### Extraction

Этот этап превращает фрагмент документа в сущности и связи. Например, модель AR-210 и деталь P-1042 становятся узлами, а утверждение об установке детали - связью между ними.

Модель возвращает JSON, структуру которого проверяет Pydantic. Затем код приводит обозначения к единому виду, сверяет номера с текстом, а названия - со словарем. Связь сохраняется, если оба конца допустимы и соответствуют ее типу. Дубликаты удаляются, а число отброшенных элементов записывается в dropped.

Если JSON некорректен, модель получает одну просьбу исправить его. После второй неудачи возвращается пустой результат. Недоступность LLM остается отдельной ошибкой сервиса.

### Communities

Чтобы отвечать на вопросы по многим документам, граф разбивается алгоритмом Лувена на сообщества - группы тесно связанных сущностей. При разбиении направления снимаются, веса встречных ребер суммируются. Фиксированный seed и упорядочивание узлов делают результат воспроизводимым. Пустой граф и изолированные узлы обрабатываются отдельно.

Для каждого сообщества модель пишет сводку до 150 слов. Статистику отказов заранее считает код по весам ребер. Модель получает готовые числа и формулирует их в тексте.

### Local search

Локальный поиск отвечает на вопросы о конкретной модели, ошибке или детали. Функции find_codes и find_names находят упомянутые сущности, которые становятся опорными точками поиска.

Между несколькими опорами выбираются пути длиной до трех связей без учета направления при обходе. Для одной опоры берется окрестность глубиной до двух. Пути дополняются цепочками замен и поставщиками новых деталей, чтобы ответ учитывал актуальную комплектацию.

Модель получает пронумерованные факты объемом до 8000 символов. Прямые связи с единственной опорой стоят перед дальними. В инструкции объясняется различие первоначальной установки детали и последующей замены.

Ответ сопровождается документами-источниками выбранных фактов. Если код из вопроса неизвестен графу или фактов нет, возвращается отказ без вызова LLM.

### Global search

Глобальный поиск отвечает на обзорные вопросы по сводкам. На шаге map модель рассматривает каждую сводку и возвращает частичный ответ с оценкой полезности по MAP_SCHEMA. На reduce полезные ответы объединяются. Некорректные ответы пропускаются. Если полезных ответов нет, система возвращает отказ.

Если названа линейка, ее модели определяются через BELONGS_TO. Сводки других линеек также обрабатываются, но их ответы исключаются из объединения, чтобы не смешивать данные разных линеек.

Код дополнительно собирает для выбранной линейки число отказов по моделям и узлам и связи исходных деталей с заменами. Эти факты передаются на map и reduce, компенсируя потери при сжатии сводок. Таким образом, поиск по сводкам расширен прямыми данными графа.

Перед выдачей коды проверяются по вопросу и использованным сообществам. Цены и количества в распознаваемых форматах без ERP отклоняются. Эта проверка не обнаруживает все ошибки связей между известными сущностями.

### Tools и agent

Агент выбирает действия для ответа. search_knowledge и summarize_topic выполняют конкретный и обзорный поиск. check_stock и get_price получают остаток и цену из ERP, а create_service_order создает заказ после подтверждения. До вызова проверяются обязательные аргументы, склад, номер детали и положительное целое количество.

Агент записывает шаги в steps и разрешает использовать детали из вопроса или предыдущих результатов. Ошибки инструментов возвращаются модели, одинаковые вызовы используют сохраненный результат. 

Неизвестная деталь, отклоненный запрос и нулевой остаток сохраняют разный смысл. При временной недоступности ErpUnavailable выполняются максимум три попытки.

В итоговом ответе коды сверяются с вопросом и результатами инструментов, цены - с полученными ценами, количества в распознаваемых форматах - с результатами проверки остатков. Неподтвержденный ответ один раз возвращается модели на исправление. Повторная ошибка приводит к отказу.

## 4. Условия оценки

Четыре режима отвечали на одинаковые 24 открытых вопроса из data/questions_dev.jsonl. Использовалась qwen3:4b-instruct-2507-q4_K_M через Ollama 0.40.14, для плоского RAG - эмбеддинги bge-m3. 

Кеш находится в artifacts/llm_cache/. Оценщик учитывает кешированные вызовы и токены как обычные, поэтому показатели отражают объем обработки, а не время повторного запуска. По открытой выборке велась и разработка. Скрытые вопросы не проверялись, поэтому качество на независимой выборке неизвестно.

### Извлечение и стоимость индекса

Качество извлечения проверено отдельно на эталоне из 16 документов. Precision показывает долю допустимых извлеченных сущностей или связей, Recall - долю найденных обязательных элементов эталона. Остальные строки описывают индекс полного корпуса.

| Документов эталона | 16 |
| Precision / Recall сущностей | 99,4% / 100% |
| Precision / Recall связей | 100% / 100% |
| Отброшено элементов на эталоне | 11 |
| Чанков полного корпуса | 92 |
| Узлов / ребер / сообществ | 122 / 279 / 12 |
| Отброшено элементов полного корпуса | 56 |

Оценщик нашел 162 связи при 161 обязательной. Это совместимо со 100% Precision, поскольку эталон допускает дополнительные корректные связи. Поле dropped объединяет отброшенные сущности и связи, поэтому сохраненная статистика не позволяет отдельно подсчитать отброшенные ребра.

В последнем прогоне индексации 103 из 104 вызовов были взяты из кеша. Поэтому число токенов характеризует стоимость обработки корпуса, но не показывает время построения индекса с нуля.

## 6. Сравнительные примеры

### Граф помогает найти актуальную замену

На dev-06 «Какую деталь заказать при ошибке E-17 на AR-210?» плоский RAG рекомендует P-1042. Он находит сведения об исходной комплектации, но не учитывает замену из бюллетеня.

Локальный поиск соединяет ошибку, узел, установленную деталь и ее замену. В результате он рекомендует P-1042B и указывает bulletin_SB-2025-03.md среди источников.

### Глобальное обобщение уступает конкретному поиску

На dev-03 «Кто поставляет деталь P-3062C?» плоский и локальный режимы правильно называют «ГидроТех». Глобальный режим называет «ХолодКомплект». В этом случае обобщение по сводкам не сохраняет точную связь детали с поставщиком, поэтому прямой поиск оказывается надежнее.

### Обзор отказов и данные ERP

На dev-13 о наиболее частом отказе в «Арктике» плоский RAG возвращает отказ. Глобальный поиск использует сводки и подсчеты по линейке и правильно называет пусковое реле с девятью отказами.

На dev-17 требуется уже не только найти деталь, но и проверить ее доступность. Агент находит P-1042B, затем получает из ERP остаток 3 штуки в Казани и цену 2630 рублей. Последовательность поиска, проверки остатка и запроса цены видна в журнале шагов.

## 7. Подтверждение человеком

При confirm=False агент возвращает needs_confirmation=True и pending_action с подготовленными аргументами, останавливая вызов ERP. Пользователь проверяет деталь, количество, модель и склад. Количество должно быть названо в запросе, иначе агент уточняет его. Деталь берется из вопроса или предыдущих результатов.

При confirm=True заказ создается, и его номер включается в ответ. Внешний интерфейс должен связывать это разрешение с конкретными показанными аргументами.

В реальном прогоне заказ двух P-2054C для BZ-120 остановился на подтверждении, и ERP не получила запрос создания. Подтвержденное создание проверено контрактным тестом.
